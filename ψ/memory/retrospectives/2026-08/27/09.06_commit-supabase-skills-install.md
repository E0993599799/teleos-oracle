## Honest Feedback

1. **`python3` vs `python` on this machine, twice in one session.** The dig.py step in
   `/recap --now`'s deep mode (not actually invoked this session, but attempted implicitly
   via the rich recap flow) and then the `/rrr` timestamp-mining step both defaulted to
   `python3`, which on this Windows/Git-Bash environment resolves to the Microsoft Store
   app-execution-alias stub, not a real interpreter. `python` (3.11.15) is the one that
   actually works. This is a per-machine PATH quirk, not a skill bug, but it cost two
   failed calls before landing on the right binary.

2. **Windows path translation for python scripts.** Git Bash's `/c/Users/...`
   MSYS-style path doesn't resolve inside a native Windows Python process — had to
   convert to a raw `C:\Users\...` string before `open()` would find the file. This
   is a recurring friction point on this specific machine (WSL/MinGW/native-Windows
   path boundary) whenever a bash-gathered path gets handed to a Windows-native tool.

3. **`/rrr`'s default background-subagent step was skipped in favor of running the
   mining command inline.** The skill instructs spawning one background Agent for
   timestamp mining; given the two path/interpreter failures already encountered, doing
   it inline (rather than debugging the same issue inside a subagent with no visibility)
   was faster for this specific short session, but it's a deviation from the documented
   default flow.

## Lessons Learned

- **On Windows/Git-Bash environments, prefer `python` over `python3` for one-off script
  calls** — `python3` frequently resolves to the Microsoft Store's app-execution-alias
  stub rather than a real interpreter, even when a working Python install exists under a
  different command name. Check both before assuming neither is installed.
- **A path gathered from Git Bash (`/c/...` MSYS style) must be converted to native
  Windows form (`C:\...`) before handing it to a native Windows-built Python** — the two
  path conventions are not interchangeable across that boundary, and a `FileNotFoundError`
  from a path that clearly exists is a strong signal this conversion was missed.
  → superseded by RTK.
- **When a `python3` (or any tool) call fails once in a session, don't re-issue the exact
  same call in a later skill invocation within the same session** — carry the failure
  forward and adjust immediately rather than rediscovering it.
- **Recap-surfaced untracked files are worth investigating even when a prior cleanup
  session already covered the vault (`ψ/`)** — a `ψ/` sweep and a `git status` sweep can
  each miss what the other catches; do both when doing repo hygiene.
