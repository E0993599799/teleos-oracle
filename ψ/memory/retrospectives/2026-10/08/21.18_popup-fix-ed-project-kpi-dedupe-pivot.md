### Key Code Changes

- `HiddenLauncher.exe`/`.cs`: a minimal C# WinExe (no console subsystem), compiled with the already-installed `csc.exe`, that re-launches a target command with `CreateNoWindow=true` and manual Windows-argv-compatible re-quoting (ArgumentList wasn't available in this Framework's reference assemblies). Used as the Action for all 5 popup-causing Scheduled Tasks.
- `supabase/migrations/20261008190000_ed_email_retrospective_import.sql`: 4 new tables (`ed_email_records`, `ed_email_attachments`, `ed_email_import_batches`, `ed_email_import_audit`), a generated `tsvector` search column, a new `manage_ed_email_import` permission (admin-only default), and 5 SECURITY DEFINER RPC functions providing functions-only read access (no RLS SELECT policy) — written but never applied to any database.

### Architecture Decisions

1. **Popup fix — compiled launcher over scripting wrappers.** `-WindowStyle Hidden` alone is insufficient for `LogonType=InteractiveToken` Scheduled Tasks (known Windows quirk); VBS/`WshShell.Run` was the natural next choice but WSH is disabled by policy on this machine. A WinExe-target compiled binary has no console subsystem at all, so there is nothing to flash — the only approach that worked. Consequence: every future hidden-Scheduled-Task fix on this machine must avoid `wscript.exe`/`cscript.exe` entirely.
2. **ED email import — functions-only DB access.** Chose to match the stricter `ed_patient_referrals` convention (SECURITY DEFINER functions, no RLS SELECT policy) over the looser existing Outlook `ed_project_*` RLS-policy pattern, because this handles the same class of PDPA-sensitive data. Not yet validated against a live database.
3. **ED email import — IMAP vs OAuth, reversed mid-session.** Initially chose IMAP over the existing Gmail App Password (since no OAuth infra existed at investigation time) — overridden by the owner, who identified that `lib/google-gmail.ts` already provides real Gmail OAuth/API access that should be reused instead. Decision reversed before any IMAP code was committed.

## Lessons Learned

- **Pattern**: When hunting for "which automated process is causing X," enumerate every plausible binary/interpreter (`powershell.exe`, `pwsh.exe`, `cmd.exe`, `wscript.exe`, etc.) in the first search pass rather than iteratively — narrowing to whichever flavor the first culprit used cost a full extra investigation round here.
- **Mistake**: Starting new integration code for a "reuse existing infrastructure" task without first running `git fetch` and checking the latest remote branch state — the existing infra can land in a commit not yet pulled, and that's a cheap check to skip when moving fast under an "autonomous, don't stop" mandate.
- **Discovery**: A diagnostic script that repeatedly re-invokes an external process to sample system state can itself become the dominant source of the very signal it's trying to detect; prefer one long-lived, self-contained sampling process over a shell loop of repeated external invocations when hunting for "what's creating new processes."
