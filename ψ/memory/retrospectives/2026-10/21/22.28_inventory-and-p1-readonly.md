## What Went Well

- ตรวจ lock + `ListAgents` + `gate-pre-result.json` ก่อนรับทั้งงาน inventory และ P1 ไม่ได้ทำตามข้อความอย่างเดียว

- พบความเสี่ยงของ `git worktree prune` บน D:/ worktree 4 ที่ มีหลักฐานจาก dry-run line และ `os.path.exists` ใต้ mapping; Khun ตรวจซ้ำ 1 ที่แล้วแก้ lock ของตัวเอง

## What Could Improve

- ใส่ DO-NOT list ของผู้สั่งในขั้นกำหนดขอบเขตการค้นหา (find) ไม่ใช่เป็นการกรองตอนแสดงผล
- สแกนที่ช้า (`/mnt/d`) ควรเขียน progress ลงไฟล์ตั้งแต่ต้นและนับจำนวนทั้งหมดจากไฟล์ ไม่ใช่อ่านจาก output ที่ถูกย่อ
- ใช้ `pgrep -f` กับ pattern ที่ปรากฏในคำสั่งของ shell ตัวเองไม่ได้ เพราะมัน match ตัวเอง

## Blockers & Resolutions

- **`powershell.exe Test-Path` (หลักฐานฝั่ง D:/)**: อาการ = ไม่มี output, `UtilAcceptVsock: accept4 failed 110` ความพยายาม = 1 ครั้ง ไม่ retry ตามข้อกำหนด ผลลัพธ์ = ใช้ `/mnt/d` mapping แทนและระบุข้อจำกัดในรายงาน ความเสี่ยงที่เหลือ: ยังไม่มีหลักฐานฝั่ง Windows จริง
- **`SendMessage` ล้ม 2 ครั้ง** แม้ `ListAgents` เห็น peer: ผมหยุดลอง บันทึกไว้ และ Khun ได้ไฟล์จาก inbox แล้วตอบ ACK ความเสี่ยงที่เหลือ: สาเหตุของความล้มเหลว UNVERIFIED
- **`pgrep -f` + `kill` ปิด shell ตัวเอง** (exit 144): แก้โดยตรวจ process ด้วย `ps` กรองตาม comm แล้วพบว่า powershell จบเองแล้ว

## Lessons Learned

- **Pattern**: เมื่อผู้ร่วมงานให้ DO-NOT list ให้เอารายการนั้นไปใส่ในขั้นกำหนดขอบเขต (เช่น `find -prune`) ก่อนรันอะไรทั้งหมด การกรองหลังรันไม่ช่วย เพราะการเข้าถึงเกิดไปแล้ว
- **Mistake**: อ่านตัวเลขจาก output ที่ถูกย่อ (`ls` ผ่านตัวกรอง) แล้วรายงานเป็นข้อเท็จจริง; ใช้ `pgrep -f` กับ pattern ที่ตรงกับคำสั่งของ shell ตัวเอง
- **Discovery**: worktree ที่สร้างจาก Windows ใช้ gitdir แบบ `D:/…` ซึ่ง git บน WSL มองว่าไม่มีอยู่ ทำให้ `git worktree prune` ฝั่ง WSL ลบ metadata ของ worktree ที่ยังใช้งานได้
