## 📝 AI Diary

The slow part of the session was almost entirely I/O: repeated long `du` scans over a large native-ext4 tree, several of which outran my first Monitor timeout and needed re-arming. I didn't mind the wait, but it padded the session with a lot of "still scanning" turns that added little value beyond patience. The genuinely interesting moment was auditing the 24 `~/wt` worktrees: my first-pass loop script computed `dirty`/`ahead`/`stashes` counts by piping git output through `wc -l` after redirecting stderr to `/dev/null` — for five worktrees whose `.git` pointer file still existed but whose backing `.git/worktrees/<name>` registry entry had been deleted, every git subcommand failed silently, and `wc -l` on empty output reported `0`, which looked *exactly* like "clean, nothing to worry about." Had I trusted that table at face value I'd have been one step from proposing deletion of possibly-live directories based on a false negative rather than a real "clean" verification. I only caught it because deleting real repos felt consequential enough to spot-check a few entries by hand with a direct `git status`, which immediately surfaced `fatal: not a git repository`. [→ AGENT DECISION] Writing the original audit loop with `2>/dev/null` and no exit-code check was the wrong call — a script meant to gate a destructive action should treat "the check itself failed" as a distinct, alarming state, not silently coerce it into the same bucket as "verified clean." ## 💭 Honest Feedback

Three friction points from this session, kept specific rather than generalized: first, the worktree-audit shell loop I wrote absorbed every git command's stderr via `2>/dev/null`, which meant a fully-failed git invocation (orphaned worktree, no registry left) and a genuinely clean worktree produced the same "0" in the `dirty`/`ahead` columns — a script-design flaw that could have led to a wrong deletion decision on real, possibly-uncommitted files had I not manually spot-checked a few entries with `git status`. Second, invoking `powershell.exe` from inside a WSL bash session required getting the quoting exactly right around `$_` — the first attempt failed with a dozen-line parser error dump before I switched to single-quoting the whole `-Command` argument, which is avoidable friction specific to this cross-shell invocation pattern. Third, several `du -sh` and `git status`/`git log` scans over the native-ext4 `/home` tree and dozens of worktrees took long enough (multiple minutes each) that the first Monitor call on each one timed out and needed re-arming with a longer window — not a correctness problem, but it added several "still waiting" round-trips to a session that was otherwise mostly analysis-then-confirm-then-execute.

## Lessons Learned

- **Pattern**: When auditing many git worktrees for delete-safety, verify with a direct `git status` (checking for a `fatal:` prefix) rather than trusting a loop that redirects git's stderr to `/dev/null` — an orphaned worktree whose `.git/worktrees/<name>` registry entry is gone will make every git subcommand fail silently, and a naive `wc -l`-on-empty-output check reads that failure as "clean" instead of "unknown."
- **Mistake**: don't wrap a PowerShell `-Command` script block in bash double quotes when it references `$_` — bash expands `$_` before PowerShell ever receives the string. Always single-quote the whole `-Command` argument when invoking `powershell.exe` from a WSL bash session.
- **Discovery**: on WSL2, a dynamically-expanding `ext4.vhdx` never shrinks on its own, even after deleting many gigabytes of files inside the Linux filesystem. Freed space only becomes real free space on the Windows host drive after `wsl --shutdown` followed by a vhdx compact (`diskpart` → `select vdisk file=...` → `attach vdisk readonly` → `compact vdisk`, or `Optimize-VHD -Mode Full` with Hyper-V tools) — and that step can only be run from outside the WSL session, since `wsl --shutdown` terminates it.
